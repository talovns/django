## 2. Доработка индивидуального проекта

Функциональная версия проекта из ПР2 (словари, списки и функции)
переработана в объектную модель. Проект не создавался заново: меню,
JSON-хранение, обработка исключений и тесты сохранены и адаптированы.

**Основные классы (пакет `models/`):**

| Класс | Атрибуты | Методы |
|---|---|---|
| `Game` — игра | `id`, `title`, `min_players`, `max_players` | `supports_players()`, `from_data()`, `__str__()` |
| `User` — игрок | `id`, `name`, `city` | `from_data()`, `__str__()` |
| `Meeting` — встреча | `meeting_date`, `city`, `place` | `from_data()`, `__str__()` |
| `GameRequest` — заявка | `id`, `game`, `author`, `players_needed`, `meeting`, `players_joined` | `free_slots()`, `add_player()`, `remove_player()`, `is_open`, `__str__()` |
| `Join` — участие в заявке | `id`, `request`, `user`, `is_cancelled` | `cancel()`, `__str__()` |

**Взаимодействие объектов.** Встреча входит в заявку: объект `Meeting`
хранится в атрибуте `GameRequest.meeting` (композиция). Заявка также
ссылается на объекты `Game` и `User` (автор), а участие `Join` связывает
объекты `GameRequest` и `User`. При записи игрока функция `create_join()`
занимает место через `request.add_player()`, при отмене метод
`join.cancel()` освобождает его через `request.remove_player()`. Отменённое
участие не удаляется из коллекции, а помечается `is_cancelled`.

**Принципы ООП в проекте:**
- инкапсуляция — счётчик участников хранится в защищённом атрибуте
  `_players_joined` и меняется только методами `add_player()` и
  `remove_player()`, снаружи доступен через `@property` только для чтения;
- полиморфизм — у каждого класса свой `__str__()`, поэтому `print(объект)`
  работает одинаково для игры, игрока, встречи, заявки и участия;
- композиция вместо наследования — сущности предметной области не
  являются разновидностями друг друга, поэтому они связаны ссылками, а не
  наследованием.

**Использованные декораторы:** `@classmethod` (`from_data()` для создания
объектов из JSON), `@property` (`players_joined`, `is_open`).

**Судьба функций ПР2:**
- стали методами: `calculate_free_slots()` → `GameRequest.free_slots()`,
  `format_meeting_info()` → `GameRequest.__str__()` и `Meeting.__str__()`;
- адаптированы к объектам: `add_request()`, `find_request()`,
  `filter_requests_by_free_slots()` (генератор), `sort_requests()` (lambda),
  `get_statistics()`, `can_join_request()`, `create_join()`, `cancel_join()`;
- остались без изменений: `get_request_status()` (из ПР1), `input_int()`,
  `input_date()`;
- добавлены: функции работы с игроками (`add_user()`, `find_user()`,
  `show_users()`) и каталогом игр (`show_games()`).

**Хранение данных.** Данные по-прежнему хранятся в JSON
(`data/games.json`, `users.json`, `requests.json`, `joins.json`). Модуль
`storage.py` при загрузке создаёт объекты и восстанавливает связи по
идентификаторам (`game_id`, `author_id`, `request_id`, `user_id`), а при
сохранении записывает вместо объектов их идентификаторы. Встреча хранится
вложенным объектом внутри заявки.

  `Meeting`, `GameRequest`, `Join`;

  словарей;

  статистика, запись в заявку и отмена участия;

- тесты переписаны под объекты: 27 тестов pytest, все проходят;
- код проверен flake8 и mypy без замечаний, pylint — 10.00/10;
- обновлён README.md, результат зафиксирован в Git (коммиты с меткой PR3).

## 4. Вывод

В ходе ПР3 проект «Сервис поиска игроков для настольных игр» переведён с
функциональной модели на объектную. Данные и связанное с ними поведение

автоматизированными тестами. Проект готов к переходу на веб-приложение
